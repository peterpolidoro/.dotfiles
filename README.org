#+TITLE: =~/.dotfiles=

This repo is the home of my custom system configuration which enables a
consistent computing experience across multiple machines. These days I primarily
use GNU/Linux via the [[https://guix.gnu.org][GNU Guix distribution]].

This setup is based on [[https://github.com/daviwil/dotfiles]]

I manage the various configuration files in this repo using [[https://www.gnu.org/software/stow/][GNU Stow]]. This
allows me to set up symlinks for all of my dotfiles using the commands:

#+BEGIN_SRC sh
# guix system
guix install git make stow
# debian
sudo apt install git make stow
rm ~/.profile && rm ~/.bashrc && rm ~/.bash_profile
rm ~/.config/xfce4/xfconf/xfce-perchannel-xml/xfce4-keyboard-shortcuts.xml
cd ~
git clone https://github.com:peterpolidoro/.dotfiles
cd .dotfiles
# install links
make install
#+END_SRC

* Routine Updates During Migration

For a Debian 13 LXQt desktop or laptop, see [[file:Desktop.org::*LXQt settings shared between machines][LXQt setup in Desktop.org]].
=make install-lxqt= installs the dotfiles and applies the shared panels,
Kitty integration, file preferences, and six xfwm4 workspaces. Run it before
the first graphical login or from a text console after logging out. Monitor
layouts and laptop power settings stay local; existing settings are backed up.

Use =upgrade-workstation --dry-run= to preview, then =upgrade-workstation= to
update the OS and user profiles from the current channel pins.  Root Guix is
separate manual maintenance via =upgrade-guix-root=, or include it with
=upgrade-workstation --root-guix=.  The old =upgrade-guix= command preserves its
previous OS + root + user behavior.

For a focused update, =upgrade-guix-user emacs= applies the channel pins and
rebuilds only the Emacs extra profile; =upgrade-profiles emacs= rebuilds it without
pulling.  Profile arguments are now honored.  See [[file:Systems.org::*Upgrading][Systems.org]] for pin updates,
Emacs payload releases, dry-run behavior, and the later Guix Home cutover.

For Guix/AppArmor trouble on a Debian machine, sync and run =upgrade-dotfiles=,
then =setup-guix-apparmor --dry-run= and =setup-guix-apparmor --check-build=. This preserves
local rules, adds build-user access when the daemon runs as root, and
reloads validated Guix profiles without restarting the daemon. Root Guix
updates run the same repair automatically. See [[file:Systems.org::*=.local/bin/setup-guix-apparmor=][Systems.org]]
for backups, supported hosts, and diagnostics.

* Work File Shares

Notes from 2026-10-20 on reaching Janelia Windows file shares and OneDrive from
the Debian + Guix desk machine. Everyone else on the team uses Windows or macOS,
so shares are published as SMB UNC paths such as =\\prfs\sciserv$=.

** Facts

- Server: =prfs.hhmi.org=. Internally it is a CNAME to
  =building.prfs.janelia.org=, which resolves to a 10.39.131.x address with a
  zero TTL (round robin). Source: =TechTips-for-New-Hires-HQ-Janelia.pdf= and
  the campus DNS.
- Login: domain =HHMI=, user =polidorop=. Local account is =peter= (uid 1001).
- Share paths are listed on https://wikis.janelia.org under "Lab and Project
  File Share Paths". The =$= suffix marks a hidden share.
- The desk is on the campus network behind the libreCMC router at
  192.168.10.1 (WAN 10.101.30.x from campus DHCP, public egress registered to
  HHMI). No VPN is needed. The PDF's VPN portal =access.janelia.org= no longer
  resolves; that section of the PDF is stale.
- Campus DNS servers from the router's WAN lease: 172.19.15.120, 172.19.15.10,
  172.18.29.60, 172.18.27.60, 172.18.27.123. Search domain =hhmi.org=.

** Router DNS forwarding (done 2026-10-20)

=prfs.hhmi.org= is an internal-only name; public DNS returns NXDOMAIN. The
router runs =https-dns-proxy= (Quad9 DoH) with =force_dns=, which redirects all
LAN port 53 traffic to the router's dnsmasq, so client-side DNS overrides do
nothing. The fix lives in dnsmasq on the router. In LuCI, Network → DHCP and
DNS:

- DNS forwardings: =/hhmi.org/172.19.15.120=, =/hhmi.org/172.19.15.10=,
  =/janelia.org/172.19.15.120=, =/janelia.org/172.19.15.10=
- Domain whitelist (rebind protection exemption): =hhmi.org=, =janelia.org=.
  Without this dnsmasq drops the private 10.x answers.

Equivalent from the router shell:

#+BEGIN_SRC sh
uci add_list dhcp.@dnsmasq[0].server='/hhmi.org/172.19.15.120'
uci add_list dhcp.@dnsmasq[0].server='/hhmi.org/172.19.15.10'
uci add_list dhcp.@dnsmasq[0].server='/janelia.org/172.19.15.120'
uci add_list dhcp.@dnsmasq[0].server='/janelia.org/172.19.15.10'
uci add_list dhcp.@dnsmasq[0].rebind_domain='hhmi.org'
uci add_list dhcp.@dnsmasq[0].rebind_domain='janelia.org'
uci commit dhcp && /etc/init.d/dnsmasq restart
#+END_SRC

The =https-dns-proxy= init script keeps =/domain/ip= entries across restarts;
it only strips plain IP upstreams, and only once when it takes its backup.
dnsmasq has "Domain required" on, so bare =prfs= never resolves. Use the full
name, or add DHCP option =119,hhmi.org= on the LAN interface so clients append
the search domain.

Verify from a LAN machine:

#+BEGIN_SRC sh
dig @192.168.10.1 prfs.hhmi.org +short     # CNAME then a 10.39.131.x address
getent hosts prfs.hhmi.org
#+END_SRC

** What is already on the machine

- Debian's =gvfs-backends= and =gvfs-fuse= are installed and =gvfsd= runs in the
  LXQt session, so =gio mount smb://...= and =smb://= URLs in PCManFM-Qt work
  without root.
- The kernel ships the =cifs= module.
- =cifs-utils= (=mount.cifs=) comes from the Guix desktop manifest, but kernel
  CIFS mounts are currently refused by the server (see below). sudo's
  =secure_path= hides Guix profiles, so give sudo the absolute path when trying.
- Guix's =samba= is old (4.18), so use Debian's =smbclient= for listing shares.
- The HHMI password lives in =pass= at =web/hhmi.okta.com=.

** Quick mount without root (GVFS): what the script does

=.local/bin/mount-sciserv= (defined in Systems.org beside =mount-janelia-misc=)
mounts the share through GVFS with the password from =pass= and links it at
=~/sciserv=. The real path is
=/run/user/1001/gvfs/smb-share:server=prfs.hhmi.org,share=sciserv$=.

#+BEGIN_SRC sh
mount-sciserv        # pinentry for gpg if the agent cache is cold
ls ~/sciserv
mount-sciserv -u     # unmount and remove ~/sciserv
#+END_SRC

Manual equivalent. The =$= in the share name must be single-quoted in bash.
=gio mount= reads user, domain, and password as three lines on stdin.

#+BEGIN_SRC sh
printf '%s\n%s\n%s\n' polidorop HHMI "$(pass show web/hhmi.okta.com | head -n1)" \
  | gio mount 'smb://prfs.hhmi.org/sciserv$'
#+END_SRC

In PCManFM-Qt, type =smb://prfs.hhmi.org/sciserv$= in the location bar and
enter user =polidorop=, domain =HHMI=.

** Kernel mount: not working as of 2026-10-21

A kernel =mount.cifs= mount fails with =mount error(13)= and the kernel log
shows =STATUS_LOGON_FAILURE= at session setup, with both =prfs.hhmi.org= and
its target =building.prfs.janelia.org=, and with the password typed by hand.
The same user, domain, and password are accepted by the Samba-based clients
(GVFS and =smbclient=, which negotiated SMB 3.0 with the server), so the
credentials are right and the server is refusing the Linux kernel client
specifically. Untried variations, each a login attempt against the account:

#+BEGIN_SRC sh
sudo ~/.guix-extra-profiles/desktop/desktop/sbin/mount.cifs '//prfs.hhmi.org/sciserv$' /janelia/sciserv \
  -o username=polidorop,domain=HHMI,uid=peter,gid=peter,vers=3.0
# or username=polidorop@hhmi.org without domain=, or sec=krb5 after kinit
#+END_SRC

If one works, switch the script back to a kernel mount, feeding the password
with =pass show web/hhmi.okta.com | head -n1 | sudo env PASSWD_FD=0 mount.cifs ...=
so it never touches the disk. =mount-janelia-misc= mounts NFS from the same
server with =sec=krb5=, so a Kerberos ticket (=kinit polidorop@HHMI.ORG=) is
the likely long-term route for kernel mounts; it needs =krb5-user=, Debian's
=cifs-utils= for =cifs.upcall=, =keyutils=, and an =/etc/krb5.conf=.

** Boot-time automount (plaintext credentials, not used)

=pass= cannot unlock the gpg key before login, so a boot-time automount would
need a root-only plaintext credentials file instead, and the kernel mount it
relies on does not currently work. Kept for reference.

#+BEGIN_SRC sh
sudo install -d -m 700 /etc/cifs
sudo tee /etc/cifs/prfs >/dev/null <<'CREDS'
username=polidorop
password=YOURPASSWORD
domain=HHMI
CREDS
sudo chmod 600 /etc/cifs/prfs
#+END_SRC

Add to =/etc/fstab= (one line), then =sudo systemctl daemon-reload= and
=ls /janelia/sciserv=:

#+BEGIN_EXAMPLE
//prfs.hhmi.org/sciserv$  /janelia/sciserv  cifs  credentials=/etc/cifs/prfs,uid=peter,gid=peter,file_mode=0664,dir_mode=0775,noauto,x-systemd.automount,x-systemd.idle-timeout=600,_netdev  0  0
#+END_EXAMPLE

** OneDrive

Office 365 includes 1 TB of OneDrive and it is the recommended backed-up
location. There is no official Linux client. Use rclone, available from apt and
Guix. =rclone config= with the =onedrive= backend opens a browser for the
Microsoft login. If the login fails with a consent error, the Office 365 tenant
blocks third-party apps and IT (support@hhmi.org, x4030) must approve rclone.

#+BEGIN_SRC sh
rclone config
rclone sync onedrive: ~/OneDrive
rclone mount onedrive: ~/OneDrive --vfs-cache-mode full
#+END_SRC
